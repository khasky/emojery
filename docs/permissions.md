# Manifest permissions

Every entry the extension declares, the code that needs it, and where it is generated. Written for people reading the source or reviewing the package; the plain-language version for users lives at [emojery.app/browser-permissions](https://emojery.app/browser-permissions), and what is collected at [emojery.app/privacy](https://emojery.app/privacy).

The manifest is generated by WXT from `wxt.config.ts` — nothing here is hand-edited per browser, and the site list is derived from the `SUPPORTED_SITES` registry (`src/shared/sites.ts`), not written out twice.

## API permissions

| Permission | Used by | Why |
| --- | --- | --- |
| `storage` | `src/shared/settings.ts` (`storage.sync`); `src/shared/target-store.ts`, `src/shared/counts-cache.ts`, `src/background/identity.ts` (`storage.local`); `src/ui/settings-cache.ts` (the content script's cached read) | Settings and the signed-in session. **The two areas differ and the difference is the point** — see below. Content scripts read the cached copy rather than asking the background on every scan. |
| `unlimitedStorage` | `src/background/history.ts`, `src/background/votequeue.ts` | Reaction history and the durable vote queue live in IndexedDB. Without it the browser's default quota can evict the queue, which would lose reactions taken offline. |
| `alarms` | `src/background/api.ts` (`vote-flush-wake`), `src/entrypoints/background.ts` (`popular-refresh`, every 6h) | An MV3 service worker is killed between events. The alarms wake it to drain queued votes and to refresh the popular-emoji list; a `setTimeout` would not survive. |
| `scripting` | `injectIntoOpenTabs` in `src/background/install.ts` | A browser injects content scripts only into pages loaded after the install, so a supported tab that was already open would stay inert until reloaded. On the install event the extension replays its own manifest content scripts into those tabs. It reaches nothing beyond the host permissions below, and runs once, on install. |
| `activeTab` | `useActiveTabUrl` in `popup-shared.tsx`, read by `popup-report.tsx`, `popup-settings.tsx` and `popup/main.tsx` | The popup reads the URL of the tab you opened it on: the Report tab prefills the page you are reporting, the Settings tab surfaces that site's own toggle, and the header swaps to its homepage variant on emojery.app. It grants nothing until the popup is open. |

### `storage.sync` vs `storage.local` — what leaves the device

Exactly one module writes `chrome.storage.sync`, and it is `src/shared/settings.ts` — the whole `Settings` object and nothing else: the master switch, the per-site toggles, the theme choice, reaction animations, "Hide original buttons" (`replaceNative`), "Auto-press original buttons" (`autoTriggerNative`), the "Community insights" consent flag (`analyticsConsent`), and the emoji-sentiment lists (which emoji you sorted as positive or negative). The browser replicates that object across the devices signed into the same browser profile, which means it passes through the browser vendor's sync service. It is a preferences blob: no reaction, no target URL, no account identifier.

Everything else is `chrome.storage.local` and never leaves the machine: the signed-in session (`auth_v1`), opaque request identifiers, the counts cache, own-reactions and auto-native records. The reaction **history** is not in `storage` at all — it is IndexedDB, also device-local (see `unlimitedStorage` above).

The split is deliberate: preferences are worth carrying to a second device, and nothing that identifies you or what you reacted to is.

## The `tabs` API, without the `tabs` permission

`chrome.tabs.*` is callable without declaring `tabs`; what the permission buys is the `url`, `pendingUrl`, `title` and `favIconUrl` fields on tabs outside the host permissions. It is not declared, so those fields arrive `undefined` for every other tab — the browser filters them, not the code. Every call site, wrapped in `src/shared/webext.ts`:

| Call | Where | What it sees |
| --- | --- | --- |
| `tabs.query({ url: ALL_SITE_MATCH_PATTERNS })`, then `tabs.sendMessage` per hit | `src/background/vote-sync.ts` | Supported-site tabs only — the cross-tab push that ticks a count up in your other open tabs. |
| `tabs.query({ url: <the manifest's own content-script matches>, status: "complete" })` | `src/background/install.ts` | The same set, once, on the install event (the `scripting` replay above). |
| `tabs.query({ active: true, currentWindow: true })` | `src/entrypoints/popup/popup-shared.tsx`, `src/entrypoints/background.ts` | One tab, the active one. In the popup that is the `activeTab` read described above; in the worker it repaints the toolbar icon after a wake, when no navigation event fires. |
| `tabs.onUpdated` / `tabs.onActivated` (+ `tabs.get`) | `src/entrypoints/background.ts` | Fires for every tab, but reads only `tab.url`. That picks the toolbar icon variant (`src/background/toolbar-icon.ts`): colored on a supported site, the homepage mark on `emojery.app`, gray everywhere else. A gray icon is the extension not knowing where you are. |
| `tabs.create` | `src/background/install.ts`, `src/background/message-router.ts` | Opens the extension's own pages and nothing else — `onboarding.html`, `auth.html`, both `chrome-extension://` URLs. |
| `tabs.executeScript` | `executeScriptFiles` in `src/shared/webext.ts` | The Firefox MV2 half of the `scripting` replay above (MV2 has no `chrome.scripting`), into the already-narrowed tabs the `install.ts` query returned. |

## Host permissions

- **The supported sites** — the match patterns derived from `SUPPORTED_SITES`; the same list the content-script entrypoints declare.
- **`https://emojery.app/*`** — the extension's own site, for the sign-in hand-off, the homepage-aware popup state, and [the presence beacon](#content-scripts).
- **The API origin** — `https://api.emojery.app` in a production build, `https://api-staging.emojery.app` in a staging build. Pinned to the build, not configurable at runtime.

The install prompt's "read and change your data" wording covers the host permissions: the extension has to see a page's action row to place the picker in it, and that is the only permission level a browser offers for that.

## Content scripts

One `src/entrypoints/<site>.content.ts` per registered site, each declaring the same match patterns as the registry row (pinned by `src/shared/content-matches.test.ts`). Those run the scan/mount pipeline — the picker.

One more runs outside that set — **the presence beacon**: `src/entrypoints/emojery.content.ts` on `https://emojery.app/*`. At `document_start` it writes the extension version to `document.documentElement.dataset`, nothing else — the marker the site's `/react` page polls to tell an installed extension from a missing one before handing off a reaction deep-link. It reads no page content and never mounts a picker.

## Optional data-collection permission

Turning the popup's "Community insights" toggle on calls `permissions.request({ data_collection: ["technicalAndInteraction"] })`, turning it off calls the matching `permissions.remove` (`src/shared/data-consent.ts`). That pair is the only permission work done at runtime, and only in a build whose manifest declares the optional bucket — the Firefox one; the Chromium builds have nothing to request, so the toggle is purely local there. It gates the optional context fields described in [amo-reviewer-build.md](amo-reviewer-build.md): a browser that refuses the request keeps the toggle off and no field is ever attached. Nothing else is requested after install — no `optional_permissions`, no optional host permissions.

## Not requested

No `tabs`, `webRequest`/`declarativeNetRequest`, `cookies`, `history`, `bookmarks`, `downloads`, `management`, `clipboardRead`, or `<all_urls>`. The extension cannot read the URL or title of any tab outside the sites above (see [the `tabs` API section](#the-tabs-api-without-the-tabs-permission)), read or modify network traffic, read cookies, or run anywhere outside the registry's hosts and `emojery.app` — where its only content script is the version marker above.

## Content security policy

`extension_pages` pins `script-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'none'`, `child-src 'none'`, and a `connect-src` limited to `'self'` plus the build's own API origin. The popup, the auth page, and the background worker hold a bearer token, so `connect-src` is the load-bearing line: an injection on an extension page has nowhere to send it.

## Web-accessible resources

`icons/*`, `emoji-data/*.json`, and `emoji-sprite/*`, exposed only to the supported-site match patterns. Content scripts fetch the emoji labels and sprite through `chrome.runtime.getURL` instead of bundling them — see [localization.md](localization.md) for why.

The per-origin `matches` gate holds on MV3 only. WXT builds Firefox as MV2, whose flat resource list has no per-origin form, so there the 3 resource groups are reachable from any page that knows the extension's origin — which Firefox randomizes per install, and nothing in the extension publishes it. The files are static, public assets either way: icons, pruned CLDR labels, and the Noto sprite.

**That "either way" is the load-bearing part, and it is pinned by a test.** Because the MV2 build cannot scope these per origin, the rule is not "scope them properly" but "never list anything here that would matter if any page could read it". `src/shared/web-accessible-resources.test.ts` fails on any addition to the list that is not one of the three known-public asset groups, so a future resource has to be argued for in review rather than inherited by a pattern edit.

## Firefox data-collection permissions

The Firefox manifest additionally declares `browser_specific_settings.gecko.data_collection_permissions`: `authenticationInfo`, `websiteContent`, and `personallyIdentifyingInfo` as required, `technicalAndInteraction` as optional. `strict_min_version` is `128.0`, below Mozilla's built-in consent flow, so the extension ships its own fallbacks for older builds — see [amo-reviewer-build.md](amo-reviewer-build.md).
